# Веб-фронтенд AlloyEditor — дизайн

Дата: 2026-10-06

## Цель и контекст

Веб-приложение для платформы AlloyEditor: рабочий инструмент для инженеров (каталог марок сплавов с химическим составом) плюс админ-панель пользователей. Бэкенд ещё дорабатывается: часть эндпоинтов и атрибутов авторизации отсутствует. Фронт делается без изменений бэкенда.

Решения, принятые с заказчиком:

- Веб-приложение, стек React + TypeScript + Vite.
- UI: MUI (Material UI), TanStack Query, React Router.
- Интерфейс на русском.
- Фронт ходит только в Gateway (`/api/gateway/...`) через nginx.
- Папка `Bredinin.AlloyEditor.Web/` в этом же репозитории, продакшен через контейнер в `docker-compose.yml`.
- Бэкенд не трогаем. Недоступные функции в интерфейсе отключены с подсказкой.

## Структура и запуск

```
Bredinin.AlloyEditor.Web/
  src/
    api/        # axios-клиент, типы DTO, функции запросов (identity, alloyGrades, alloySystems, dictionary, admin)
    auth/       # AuthProvider, хранение токенов, декод JWT (роли), RequireAuth / RequireRole
    features/   # login, alloy-grades, alloy-systems, elements, users
    components/ # Layout (шапка + меню), ConfirmDialog, ErrorAlert
    main.tsx, router.tsx, theme.ts
  Dockerfile, nginx-web.conf, vite.config.ts, .env.example
```

- Разработка: `npm run dev`; Vite проксирует `/api/*` на nginx или Gateway (настраивается в `vite.config.ts` и `.env`).
- Продакшен: многоступенчатый `Dockerfile` (сборка Node, затем nginx со статикой). В `docker-compose.yml` добавляется сервис `web`. В основном `nginx.conf` добавляется `location /` для статики; существующие правила не меняются. CORS не нужен.
- Все запросы идут относительными путями `/api/gateway/...`.

## Авторизация

- `POST /api/gateway/identity/login` принимает `{login, password}`, возвращает `{accessToken, refreshToken}`.
- Роли берутся из JWT-клейма `ClaimTypes.Role` (`http://schemas.microsoft.com/ws/2008/06/identity/claims/role`), строка или массив. Идентификатор пользователя берётся из клейма `sub` (или `userId`, по факту токена).
- Access-токен хранится в памяти, refresh-токен в `localStorage`. При загрузке страницы выполняется обмен refresh на новую пару.
- Axios-интерцептор: `Authorization: Bearer ...`; при 401 один раз вызывает `refresh-token`, повторяет запрос; параллельные запросы ждут единственного обновления. При неудаче выход и переход на `/login`.
- `RequireAuth` защищает приложение, `RequireRole("Admin")` защищает раздел пользователей и скрывает пункт меню. Точное имя роли проверяется по сидам миграции `2025_08_25_2116_InsertValuesInTables` при реализации. Реальную защиту обеспечивает бэкенд.
- Выход удаляет токены локально (эндпоинта logout нет). `revoke-access` используется только в админке.
- Временная особенность бэкенда: неверный логин приходит как 500. Форма входа показывает «Неверный логин или пароль» при 401 и при 500 на эндпоинте login. Убрать, когда бэкенд начнёт отдавать 401.

## Экраны

1. **Вход** (`/login`): логин и пароль, ошибка под полем.
2. **Каталог марок** (`/grades`, главный):
   - Таблица: название, система сплава, описание, число элементов состава; поиск по названию, фильтр по системе.
   - Карточка марки: состав (элемент, мин, макс, точное значение), термообработка и механические свойства, если есть в ответе.
   - Удаление с подтверждением.
   - Создание: название, описание, система сплава, редактор состава. Клиентская валидация повторяет правила бэкенда: базовый элемент системы обязателен, без дубликатов элементов, сумма не больше 100%, значение задаётся либо точное, либо диапазон мин и макс. Блоки термообработки и механических свойств уходят пустыми.
   - Редактирование: кнопка отключена с подсказкой «Недоступно: нет эндпоинта в Gateway».
3. **Системы сплавов** (`/systems`): таблица только для чтения (название, базовый элемент, описание); клик показывает марки через `for-main-element/{id}`.
4. **Справочник элементов** (`/elements`): таблица только для чтения (символ, название, атомный номер, масса, группа, период, плотность), поиск, бейдж базового элемента.
5. **Пользователи** (`/users`, только админ): таблица из `search-users`; создание и изменение в диалоге; удаление с подтверждением; «Отозвать доступ»; «Сбросить пароль» отключено до появления обработчика на бэкенде.

Эндпоинты Gateway, которые используются: `identity/login`, `identity/refresh-token`, `identity/{userId}/revoke-access`, `alloy-grade` (GET, POST, DELETE, `for-main-element/{id}`), `alloy-system` (GET), `dictionary/chemical-elements`, `admin/*`.

Не входит, потому что Gateway этого не отдаёт: справочники типов термообработки и типов механических свойств, редактирование марки, сброс пароля.

Состояния загрузки, ошибки и пустых данных обязательны на всех таблицах; уведомления об успехе и ошибке через Snackbar.

## Ошибки

- Единый слой в axios приводит ошибку к `{status, message}`; `BusinessException` бэкенда приходит как 4xx с текстом, остальное как 500 с `ex.Message`.
- 401: обновление токена и выход; 403: «Недостаточно прав»; 429: «Слишком много запросов, повторите позже»; сеть и 5xx: общий текст.
- `ErrorBoundary` на уровне роутера с кнопкой «Обновить».
- TanStack Query не повторяет запросы при 4xx, при 5xx один повтор.

## Тестирование

- Vitest + React Testing Library + MSW (мок HTTP), реальный бэкенд не нужен.
- Покрытие рискованного: логика токенов (автообновление при 401, очередь параллельных запросов, выход при неудаче), валидация состава сплава, `RequireAuth` и `RequireRole`, форма входа, создание марки.
- `npm run lint` (ESLint + `tsc --noEmit`) и `npm test`; сборка и тесты запускаются перед сообщением о готовности.

## Границы (YAGNI)

- Без SSR, i18n-библиотеки, тёмной темы, Redux.
- Состояние: React state, Context для авторизации, TanStack Query для данных сервера.
- Типы DTO пишутся вручную по контрактам C#; кодогенерация из Swagger возможна позже.
- Когда бэкенд получит недостающие эндпоинты, подключаются: редактирование марки, сброс пароля, термообработка и механические свойства.

## Известные проблемы бэкенда (вне объёма)

- Админские эндпоинты Gateway и WebApi открыты без `[Authorize]`.
- WebApi не регистрирует JWT-аутентификацию.
- У `ResetPasswordUserCommand` нет обработчика.
- В `nginx.conf` жёсткий лимит для входа задан на `/api/identity/login`, а реальный путь `/api/gateway/identity/login`.
