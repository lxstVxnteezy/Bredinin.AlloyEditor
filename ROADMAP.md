### Исправлено в валидации

- **Сумма максимумов больше не ограничивается 100%.** Раньше марка «Fe 95–99 %, C 0.5–1 %, Cr 1–5 %» отклонялась. Ограничена только сумма нижних границ.
- Лимит значения элемента 99 → **100** (база сплава может быть 99.99 %).
- Нельзя одновременно `ExactValue` и `Min/Max`; нельзя дублировать элемент в составе.
- Единый базовый класс правил строки состава вместо копипасты в двух валидаторах.
- **Новые валидаторы:** термообработка (создание и обновление), механические свойства (создание и обновление), обновление марки, все команды Identity (логин, пароль ≥ 8 с буквой и цифрой, возраст, роли без дублей).
- Лимиты длин приведены к размерам колонок БД.
- Хендлеры механических свойств теперь проверяют `MinPossible/MaxPossible` из справочника (поля были, но не использовались) и `Min ≤ Max`.
- Валидация подключена в `Identity.Service` (раньше только в `WebApi`).

> **Поведение изменилось:** запросы с `ExactValue` вместе с `Min/Max`, дублями элементов, паролем короче 8 символов или возрастом вне 14–100 теперь получают 400. Если UI или импорт слали такое — их нужно поправить. Границы возраста и сложность пароля — в `IdentityRules.cs`.

## 1. Найдено, но не исправлено (требует вашего решения)

Сортировка по риску.

### Критично

1. **Нет авторизации на эндпоинтах.** `[Authorize]` стоит только на `DictionaryGatewayController`. Создание и удаление пользователей, сброс пароля, отзыв токенов, CRUD сплавов доступны **без токена**, причём и через gateway, и напрямую к сервисам (порты 5019/5020). Нет и проверки ролей (`Admin`). Роли попадают в JWT, но нигде не используются.
2. **Секреты в git.** `.env` (пароли PostgreSQL, `JWT_KEY`) и `Common.Authentication/Configs/jwtSettings.json` (ключ подписи) закоммичены. Ключ нужно считать скомпрометированным: сменить и вынести в секреты.
3. **Создание марки теряет данные.** `CreateAlloyGradeRequest` принимает `HeatTreatments` и `DefaultMechanicalProperties`, `CreateAlloyGradeHandler` их молча игнорирует (валидатор теперь их проверяет, но сохранять некому).

### Важно

4. **Справочник химэлементов в уже развёрнутых БД мог быть засеян с ошибкой ×1000** (баг №3). Нужна миграция-исправление и проверка `atomic_weight`/`density` на проде.
5. `ErrorHandlingMiddleware` отдаёт клиенту `ex.Message` при 500 (утечка внутренностей).
6. Частичное обновление (`PUT` термообработки и свойств) не проверяет согласованность итогового состояния: можно получить `Exact` и `Min/Max` одновременно. Нужна проверка слитого результата в хендлере (для свойств уже сделана).
7. Gateway не пробрасывает `Authorization` в downstream (Refit без `AuthorizationHeaderValueGetter`). Работает только потому, что сервисы не проверяют токен (п. 1).
8. `TokenRevocationMiddleware`: токен, выпущенный в ту же секунду, что и отзыв, не считается отозванным (`<` вместо `<=`); `long.Parse` без защиты.
9. Нет CI (`.github/` отсутствует).

### Гигиена

10. Мёртвый и дублирующий код: `Identity.Service.Core.Http` (своя копия `ErrorHandlingMiddleware` и `BusinessException`), `Core.Authentication` (старый `JwtProvider`), пустой `RegisterUserCommand`, пустые `BusinessMetrics` и `Identity.Service.Core.BackgroundService`.
11. Тестовый эндпоинт `GET /api/admin/test` с `Task.Delay(5000)` — убрать.
12. Опечатки в именах: `Bredinin.AlloyEdtior.Handlers.Tests`, `MechenicalProperties`, `descrpition`.
13. Версии старых миграций записаны в формате `yyyyddMM` (например, `202504062208` для 2025-06-04). Менять нельзя — они уже применены; новые писать в `yyyyMMddHHmm`.
14. Контроллеры возвращают `Task<T>` без `ActionResult`, разные стили (`Ok(...)`, голые модели) — стоит унифицировать.

## 2. План развития

### Фаза 1 — Укрепление (1–2 недели)

Цель: сервис безопасно выпускать наружу.

- [ ] Ротация `JWT_KEY` и паролей БД; `.env` и `jwtSettings.json` убрать из git, секреты через переменные окружения или Docker secrets.
- [ ] Авторизация: `[Authorize]` на всё, `[Authorize(Roles = "Admin")]` на `AdminController`; в WebApi и Identity — тоже, не только в gateway. Закрыть прямой доступ к портам в `docker-compose` (сейчас наружу опубликованы сервисы 5019/5020, PostgreSQL 5432/5433 и Redis 6379), оставить только NGINX.
- [ ] Пробрасывание токена gateway → сервисы.
- [ ] Починить «потерю данных» при создании марки (п. 1.3): сохранять термообработки и свойства, транзакционно.
- [ ] Миграция-исправление справочника элементов (п. 1.4).
- [ ] CI (GitHub Actions): restore → build → test → coverage-порог → сборка Docker-образов.
- [ ] Убрать мёртвый код (п. 1.10–1.12), починить опечатки.
- [ ] Rate limiting и lockout на `/login` (подбор паролей).

**Критерий готовности:** без токена все эндпоинты отвечают 401; CI зелёный; тест на каждый защищённый маршрут.

### Фаза 2 — Веб-клиент (3–5 недель)

- **Стек:** React + TypeScript + Vite (или Blazor, если хотите остаться на .NET). Клиент API генерируется из Swagger (`openapi-typescript`), контракты не дублируются руками.
- **Раздача:** статика через тот же NGINX; запросы только на `/api/gateway/*`.
- **Экраны:** вход → каталог сплавов (поиск и пагинация уже есть на бэкенде) → карточка марки (состав, термообработки, свойства) → редактор → админка пользователей.
- **Состояние и токены:** access в памяти, refresh в httpOnly-cookie (потребует правки Identity); автообновление по 401.
- **Тесты:** Vitest + Playwright (Chromium уже есть в окружении).

**Критерий готовности:** полный сценарий «войти → найти марку → отредактировать состав → выйти» проходит в e2e.

### Фаза 3 — База знаний (4–6 недель)

Отдельный сервис `Knowledge.Service` со своей БД (по образцу Identity).

- **Модель:** `Article` (Markdown, версии, статус черновик/опубликовано), `Tag`, `Attachment`, связи многие-ко-многим со `AlloyGrade`, `AlloySystem`, `HeatTreatmentType`, `MechanicalPropertyType`.
- **Поиск:** PostgreSQL FTS (`tsvector` + словарь `russian`); если упрётесь — OpenSearch.
- **Файлы:** MinIO (S3-совместимое) в `docker-compose`; ГОСТы и PDF.
- **Права:** `KnowledgeEditor` пишет, остальные читают.
- **В карточке марки:** вкладка «Знания» со связанными статьями.
- **API:** `/api/knowledge/*` через gateway; маршруты проверяются тем же контрактным тестом.

**Критерий готовности:** статью можно привязать к марке и найти полнотекстовым поиском по русскому тексту.

### Фаза 4 — Платформа и надёжность (параллельно)

- **Интеграционные тесты** с Testcontainers (PostgreSQL + Redis): прогон всех миграций с нуля, проверка, что `EnsureCreated`-схема совпадает с миграциями, тесты уникальных индексов и каскадов на реальном Postgres.
- Контрактные тесты Gateway ↔ сервисы расширить на типы ответов, а не только маршруты.
- Health-checks (`/health/live`, `/health/ready`), алерты в Grafana (5xx, p95, рост ошибок логина).
- Структурные логи с `correlation-id` через gateway.
- Резервные копии: у вас уже есть `backup/` — автоматизировать и проверять восстановление.

### Фаза 5 — ML-сервис (5–8 недель, можно начинать исследование раньше)

**Шаг 0 — данные (до любой разработки).** Выгрузить датасет «состав + термообработка → механические свойства» и оценить: сколько марок с заполненными свойствами, есть ли разброс, какие свойства покрыты. Если меньше нескольких сотен записей, сначала нужно нарастить данные (импорт из ГОСТов, база знаний), иначе модель будет предсказывать шум.

- **Сервис:** Python 3.12 + FastAPI в отдельном контейнере, не публикуется наружу, вызывается из gateway по `IMlClient` (Refit).
- **Модели:** градиентный бустинг (LightGBM/XGBoost) с квантильной регрессией для доверительных интервалов; для малых данных — Random Forest или GP. Нейросети на таких объёмах не нужны.
- **Признаки:** доли элементов (с учётом диапазонов — середина и ширина), температура и время ТО, среда охлаждения, система сплава.
- **Эндпоинты:** `POST /predict` (состав + режим → свойства с интервалом), `POST /recommend` (целевые свойства → ближайшие марки и режимы), `GET /models` (версии, метрики).
- **Жизненный цикл:** обучение по расписанию, версии моделей в реестре (MLflow или таблица в БД), метрики качества в Prometheus, сравнение предсказаний с реальными значениями после их ввода.
- **Защита:** валидация входа (те же правила состава, что и в .NET: сумма ≤ 100, диапазоны), отказ с пониженной уверенностью вне области обучения.
- **UI:** форма «задать состав → получить свойства с интервалом» и честная подпись «оценка модели, не результат испытаний».

**Критерий готовности:** на отложенной выборке MAE по ключевым свойствам не хуже заранее согласованного порога, а модель в UI показывает неопределённость.

### Фаза 6 — RAG поверх базы знаний (после 3 и 5)

- Эмбеддинги статей в `pgvector`, поиск по смыслу, ответы на вопросы с цитатами на статьи.
- Объединение с ML: «подбери сплав под требования» → кандидаты из ML + обоснование из статей.

## 3. Рекомендуемая очередь

1. Фаза 1 целиком (безопасность не ждёт).
2. Шаг 0 фазы 5 (оценка данных) параллельно, он ничего не ломает и определяет реалистичность ML.
3. Фаза 2 → Фаза 3.
4. Фаза 4 идёт фоном; CI из Фазы 1 — первый шаг.
5. Фазы 5–6 после появления веб-клиента и базы знаний: им нужны и данные, и интерфейс.
